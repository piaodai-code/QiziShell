# Chrome Keep-alive：保活维护

这份说明给维护保活的 Agent（Maintainer）。日常发布的 Agent 不看这份，看同目录的《日常发布》。

你负责：把保活服务跑起来、写和更新保活脚本、掉线后重新登录、页面改版后改脚本。你不负责发帖。

## 启动保活服务

保活服务是这台服务器上的一个 Node 进程。QiziShell 在另一台 Mac 上，只用来看状态，不能代替启动。

### 前提

在这台机器上确认两件事：

```
node -v
```

需要 Node.js 18 或更高。

这台机器的用户要处于已登录的图形界面。用屏幕共享看着也算。停在登录窗口时，保活窗口起不来。不要安装或启动系统里的 Google Chrome 来跑保活。

### 第一次安装

如果当前目录里已经有 `server.js` 和 `package.json`，跳过这一节，直接启动。

安装包文件名是 `qizi-keepalive-server-0.2.0.tgz`。在你要放置它的目录执行：

```
tar -xzf qizi-keepalive-server-0.2.0.tgz
cd qizi-keepalive-server
npm install --omit=dev
```

`npm install` 会下载保活窗口用的内置浏览器。微信视频号和小红书在同一个窗口里，收在菜单栏。窗口顶上「保活」一组是这两个平台的常驻页。视频号的登录留在这个窗口里。小红书第一次收进来时，要在窗口里重新扫码。

### 启动

在含有 `server.js` 的目录执行：

```
mkdir -p ~/.qizi-keepalive
nohup node server.js >> ~/.qizi-keepalive/keepalive.log 2>&1 &
```

想盯着日志看，就前台运行 `node server.js`。这个终端关掉，保活服务就停了。保活窗口不会跟着停。

第一次启动会在程序目录里生成「保活」图标。关闭按钮和菜单栏「收起」只是收进菜单栏，点菜单栏图标或「展开」就能看见。菜单栏「退出」会关掉窗口；服务还在、开关还开着时，窗口会自己再打开。想马上打开，双击这个图标。服务没在跑时，双击图标会把服务启动起来。不要为了看窗口再执行一次 `node server.js`。

启动成功时，日志里有这一行：

```
keep-alive server listening on 0.0.0.0:18990
```

### 确认已经在跑

```
curl -s http://127.0.0.1:18990/api/state
```

返回的 JSON 里 `"ok": true` 就是在跑。`platforms` 是空数组也正常：平台要在 QiziShell 的 Chrome Keep-alive 窗口里添加，启动本身不创建平台。

### 已经在跑就不要再启动

再执行一次 `node server.js` 会因为端口被占用而退出，日志里是 `port 18990 is already in use`。先用上面的 `curl` 看现有进程，不要开第二个。

查正在监听的进程：

```
lsof -nP -iTCP:18990 -sTCP:LISTEN
```

### 停掉服务

停的是 Node 进程。保活窗口继续开着，下次启动会接管它。不要结束 Electron 进程。

```
kill <上面 lsof 看到的 pid>
```

### 现在这个阶段

机器重启后保活服务不会自己起来，需要再执行一次启动命令。保活服务在跑的时候，保活窗口崩溃或被关掉，会自动重新拉起。

### 数据放在哪

默认目录 `~/.qizi-keepalive/`：

| 路径 | 内容 |
| --- | --- |
| `config.json` | 平台配置 |
| `state.json` | 开关、暂停、占用锁 |
| `scripts/<平台ID>.json` | 你提交的保活脚本 |
| `shell/` | 所有平台共用的保活窗口，登录留在这里 |
| `downloads/` | 在保活窗口里下载的文件 |
| `keepalive.log` | 运行日志 |

换端口或换数据目录：

```
node server.js --port 18990 --data-dir ~/.qizi-keepalive
```

## 地址与响应

接口在本机，默认端口 18990。通知消息里给出的地址是实际在用的端口。

```
http://127.0.0.1:18990
```

请求体和响应体都是 JSON。成功时 `ok` 为 `true`。失败时 `ok` 为 `false`，`error` 是一句中文原因。状态码：400 参数不对，404 没有这个平台，409 与当前状态冲突，502 浏览器或下游没配合。

下文 `{id}` 是平台 ID，例如 `channels_01`。

所有 `browser` 为 `shell` 的平台共用一个保活窗口，收在菜单栏里。连接只用 `status.cdp_http`，各平台是同一个地址。平台配置里的 `cdp_port` 不是这个窗口的监听端口，不要拿去连。`status.shared_window` 为 `true` 时，`status.cdp_port` 才是窗口正在用的端口，`chrome_pid` 是共享窗口的进程。`GET /api/platforms/{id}` 的 `pages` 只含这个平台的页签：`group` 为 `keepalive` 的是保活页，`work` 是临时页。要人扫码时，让用户看服务器的屏幕。

## 找到保活窗口

```
GET /api/platforms
GET /api/platforms/{id}
```

`GET /api/platforms/{id}` 的响应里，用这些字段：

- `platform.status.browser_alive`：这个平台的保活页是否在窗口里
- `platform.status.cdp_http`：CDP 地址，例如 `http://127.0.0.1:9333`。shell 模式下各平台相同
- `platform.status.shared_window`：为 `true` 时配置里的 `cdp_port` 不要拿来连接
- `pages`：只含这个平台。`group` 为 `keepalive` 的保活页不要关
- `cdp_ws`：浏览器级 WebSocket 地址
- `pages`：当前页签的 `id`、`url`、`title`
- `platform.status.session.status`：`alive` 已登录，`logged_out` 确认掉线，`unknown` 没判断出来。`session` 为 `null` 表示还没检测，或没有可用脚本
- `platform.status.script`：`state` 为 `ok`、`missing` 或 `invalid`。`invalid` 时 `error` 写明脚本错在哪
- `platform.status.lock`：谁占着、何时自动解除。`null` 表示没人占

`browser_alive` 为 `false` 时不要自己启动浏览器。请用户在 QiziShell 的 Chrome Keep-alive 窗口里打开这个平台。窗口没开着时，你也可以：

```
curl -s -X POST http://127.0.0.1:18990/api/platforms/{id}/chrome \
  -H 'Content-Type: application/json' -d '{"on":true}'
```

关掉用 `"on": false`。

## 占用锁

保活到点会点击平台页面。你登录或改脚本、对着页面试选择器之前，先占锁，做完立刻解锁。发布 Agent 使用同一把锁，规则在《日常发布》里。

`owner` 用你自己的身份，固定写 `maintainer`，不要和发布 Agent 混用。

```
POST /api/platforms/{id}/lock
{ "owner": "maintainer", "reason": "重新登录", "ttl_minutes": 30 }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `owner` | 是 | 解锁时必须用同一个值 |
| `reason` | 否 | 显示在监控窗口里 |
| `ttl_minutes` | 否 | 1–1440。不填则用该平台的默认值，初始 10 分钟。登录可能超过 10 分钟，按需要填大 |

收到 `ok: true` 之后才能操作页面。请求到达时若有一轮保活正在执行，会等那一轮结束再返回。

锁快到期就用同一个 `owner` 再调一次 `lock`，从当前时刻重新计时。别人占着时返回 409，`error` 里写明是谁、最晚何时解除。等它解除，不要强行操作。

```
POST /api/platforms/{id}/unlock
{ "owner": "maintainer" }
```

解锁后几秒，保活服务会只读地看一眼页面。登录成功的话，它自己恢复定时保活。

锁到期会自动解除。那是防止占用方中途消失后保活永远停着，不是正常的解锁方式。

## 操作保活窗口时的约定

- 保活使用和入口网址同主机名的那个常驻页，在窗口顶上「保活」一组里。调试时用 `window.open(完整网址)` 在这组外面开一个临时页，用完关掉。
- 不要 `browser.newPage()`。那样开出的窗口没有这份登录。
- 不要关掉保活那个页签，也不要把它导航到别的网站。另一个平台的常驻页同样不要动。
- 不要退出窗口，不要清除 Cookie。

## 保活脚本

每个平台一份 JSON。`keepAlive` 是到点做的动作，`detect` 是登录状态的特征。保活服务不内置任何平台的动作。没有脚本时，它只维持保活窗口里的这个页，不点击，也不判断登录。

页面改了，你改这份脚本。保存后从下一轮开始生效。

### 提交和读取

```
PUT /api/platforms/{id}/script
GET /api/platforms/{id}/script
```

`PUT` 的请求体就是脚本本身。不合格时返回 400，`error` 指出哪个字段不行，原来的脚本不变。

`GET` 的 `state`：`ok`、`missing`（还没有）、`invalid`（文件有错误，看 `error`）。`script` 是当前文件内容。

文件同时在 `~/.qizi-keepalive/scripts/{id}.json`。用接口提交，不要手改到一半留下非法 JSON。

### 示例

选择器和错误码只是示意，必须对照真实页面核实后再用。

```json
{
  "keepAlive": {
    "steps": [
      { "action": "click", "selector": "text=数据中心" },
      { "action": "wait", "ms": [3000, 8000] },
      { "action": "click", "selector": "text=内容管理" }
    ]
  },
  "detect": {
    "loginUrlPattern": "/\\/login|passport/i",
    "requiredUrlSubstr": "/platform",
    "logoutTextPattern": "微信扫一扫登录|扫码登录|登录已过期|请重新登录|微信快捷登录|登录视频号助手",
    "qrSelector": "iframe[src*=\"login\"], .login-qrcode",
    "aliveSelectors": ["text=内容管理", "text=发表视频"],
    "apiHostFilter": "channels.weixin.qq.com",
    "apiAuthErrorCodes": [300334]
  }
}
```

### `keepAlive.steps`

按顺序执行，最多 50 步。目的是让页面自己向平台发出带登录凭据的请求。保活服务不直接调用平台接口。

| `action` | 字段 | 作用 |
| --- | --- | --- |
| `open` | `url`（可选） | 导航到 `url`；不填则用平台入口网址 |
| `reload` | 无 | 刷新当前页 |
| `click` | `selector`（必填）、`timeout_ms`（可选，500–60000，默认 10000）、`optional`（可选） | 点击第一个匹配元素 |
| `wait` | `ms`（必填） | 等待。一个数字是固定毫秒；`[最短, 最长]` 每次在范围内随机。上限 120000 |

选择器是 Playwright 写法：`.nav-item`、`a[href*="data"]`，或 `text=数据中心`。

某一步失败，这一轮停在那里，记为动作没跑完。`click` 加上 `"optional": true` 时，找不到就跳过，后面的步骤继续。

写的时候：

- 优先在后台内部切换栏目。`reload` 和 `open` 放在其次。
- 动作之间加 `wait`，并用 `[最短, 最长]`。保活服务每一轮的触发时刻自己也有随机漂移。
- 最后一步停在后台首页或某个稳定栏目，让 `aliveSelectors` 看得见。

### `detect`

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `aliveSelectors` | 是，至少一个 | 只有登录后才看得到的元素。任意一个可见即已登录 |
| `loginUrlPattern` | 否 | 登录页网址的正则。配了二维码或掉线文案时，要等其中一种登录界面出现才算掉线 |
| `logoutTextPattern` | 否 | 掉线时才出现的文案的正则。视频号要同时覆盖二维码页和「微信快捷登录」卡片 |
| `qrSelector` | 否 | 登录二维码或登录框。可见即掉线 |
| `requiredUrlSubstr` | 否 | 后台网址必含的片段。不含则这一次判不出来，不算掉线 |
| `apiHostFilter` | 否 | 只监听网址包含这段文字的请求 |
| `apiAuthErrorCodes` | 否 | 平台接口表示未登录的业务错误码 |
| `apiAuthErrorFields` | 否 | 错误码在 JSON 里的字段，默认 `["errCode", "code"]`。嵌套用点号，如 `base_resp.ret` |
| `apiAuthHttpStatuses` | 否 | 表示未登录的 HTTP 状态码，默认 `[401]` |

`loginUrlPattern`、`logoutTextPattern`、`qrSelector`、接口错误码，至少要有一类。

正则写成字符串：`"扫码登录|请重新登录"`，或 `"/\\/login|passport/i"`。

判断顺序，命中即停：

1. 网址匹配 `loginUrlPattern`，并且二维码已经可见，或页面上已经有 `logoutTextPattern` 里的文案（例如「微信快捷登录」）→ 掉线
2. 网址匹配 `loginUrlPattern`，但二维码和这些文案都还没出现 → 没判断出来。页面刚打开时会先经过登录网址，马上又跳进后台
3. 这一轮保活期间，平台接口返回了未登录的状态码或错误码 → 掉线
4. 页面可见文字匹配 `logoutTextPattern` → 掉线
5. `qrSelector` 可见 → 掉线
6. 设了 `requiredUrlSubstr` 而网址不含它 → 没判断出来
7. 任意一个 `aliveSelectors` 可见 → 已登录
8. 以上都不是 → 没判断出来

视频号掉线有两种界面，都要写进脚本：一种是二维码，一种是头像加上「微信快捷登录」按钮。只认二维码会把第二种漏掉。

「没判断出来」会隔 4 秒重试，最多两次，不会因此叫你去登录。两次之后若仍停在登录网址上，再算掉线。

窗口刚打开后的第一次检测等 15 秒，给页面留出从登录网址跳进后台的时间。

第 3 条只在执行保活动作的那一轮生效。要靠错误码发现掉线，步骤里必须有能让页面发请求的动作。

误判会停掉保活并给你发登录通知：

- `logoutTextPattern` 匹配整个页面的可见文字。选掉线时才出现的完整句子。
- `apiAuthErrorCodes` 只填确认代表未登录的码。

### 写完后验证

占着锁时立刻跑一轮，不必等定时。`owner` 要和占锁时相同，否则会因为锁被占用而跳过。

```
POST /api/platforms/{id}/keepalive
{ "owner": "maintainer" }
```

`keepalive.result`：

| 值 | 含义 |
| --- | --- |
| `ok` | 步骤都执行了 |
| `action_failed` | 某一步失败。看 `steps` 里 `ok` 为 `false` 的那项的 `error` |
| `skipped_locked` | 锁被别人占着。自己占着时要带上 `owner` |
| `no_script` | 没有可用脚本 |
| `error` | 这一轮整体出错，原因在 `error` |

只看登录状态、不动页面：

```
POST /api/platforms/{id}/check
```

合格标准：已登录时 `result` 为 `ok` 且 `detection.status` 为 `alive`；你也对照过掉线页面会被判为 `logged_out`。

## 你会收到的两类消息

都发到 Maintainer 会话，以 `【Chrome Keep-alive】` 开头。QiziShell 不再单独要一套通知账号。

这台机器上 Hermes 面板是 `http://127.0.0.1:9119`。`config.json` 里的 `notify.hermes_url` 必须是这个本机地址（或同机的其他回环地址）。公网名字在这台机器上解析不了，写进去会被改成 `http://127.0.0.1:9119`。密码有首尾空格时会去掉；保存时密码留空则保留已存的密码。

本机地址已填好时，保活服务自己把消息发到 Hermes。失败会在 `keepalive.log` 里留下 `notify failed url=... error=...`，`GET /api/state` 的 `notify.reachable` 为 `false`、`notify.last_error` 是错误首行。本机没发出去时，QiziShell 再用它已经登录的 Maintainer 补发。

### 「××掉线，请去重新登录」

保活已经确认掉线，并停止点击这个平台。消息里有判定依据、当前页面、CDP 地址。

1. `lock`，`ttl_minutes` 按登录需要的时间填。
2. 用 `cdp_http` 连进保活窗口，在这个平台的保活页上完成登录。要人扫码时，告诉用户到服务器屏幕上扫。不要 `browser.newPage()`。
3. `unlock`。

解锁后它自己发现会话恢复。同一次掉线只通知一次。你没处理时，它每分钟只读看一眼，不会连着发消息。

### 「保活脚本连续 3 轮没跑通」

连续三轮定时保活出现步骤失败或判断不出登录状态，并且不是掉线。通常是页面改版。消息里有最近一轮失败在第几步、报了什么错。

1. `lock`。
2. 用 `cdp_http` 连进保活窗口，看这个平台的保活页。
3. 改脚本，`PUT` 上去，再 `POST …/keepalive`，直到 `result` 为 `ok`、`detection.status` 为 `alive`。
4. `unlock`。

新脚本提交后，失败计数清零。同一段连续失败只通知一次。

## 新平台从零开始

1. 用户在 QiziShell 的 Chrome Keep-alive 窗口添加平台，并打开它。新平台也进同一个保活窗口。
2. 你 `lock`，用 `cdp_http` 连进保活窗口，在这个平台的保活页上完成首次登录。
3. 对照登录后的页面写 `keepAlive.steps` 和 `aliveSelectors`；对照登录页写掉线依据。
4. `PUT` 脚本，`POST …/keepalive` 验证。
5. `unlock`。之后按间隔自动执行。

## 开发调试时看哪里

服务在跑、行为不对时，按这个顺序看：

1. `~/.qizi-keepalive/keepalive.log` 里该平台 ID 最近的行。
2. `curl -s http://127.0.0.1:18990/api/platforms/{id}`，看 `browser_alive`、`session`、`script`、`lock`、`last_keepalive`。
3. 脚本被拒或显示有错误：`GET /api/platforms/{id}/script` 的 `error`。
4. 想马上看一轮真实点击的结果：先 `lock`，再 `POST …/keepalive`，看返回的 `steps`。
5. 保活窗口在服务器屏幕上，可以收在菜单栏里。这台 Mac 的 QiziShell 里看不到那个窗口。
